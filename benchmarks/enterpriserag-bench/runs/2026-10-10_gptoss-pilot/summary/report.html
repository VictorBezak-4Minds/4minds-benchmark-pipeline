EnterpriseRAG-Bench · PILOT

Benchmark: onyx-dot-app/EnterpriseRAG-Bench on GitHub

Does 4Minds answer questions about a company's own documents better than the RAG systems that customers already use? 9 systems with the same model (GPT-OSS-120B) answered the same 50 questions from the same 10,000 company documents. The official EnterpriseRAG-Bench scorer, with its own judge (gpt-5.4), scored each system alone.

Method

How the benchmark ran

Protocol

  • Dataset: EnterpriseRAG-Bench (Onyx), commit d36685e27371, 511,958 documents and 500 questions.
  • Pilot: 50 questions, stratified by question type, seed 42.
  • Corpus slice: the 74 gold documents of the pilot questions plus 9,926 random other documents (48,872,100 characters).
  • Every system got the same documents and the instructions of the official answer prompt.
  • Scoring: the official metrics_based_eval.py, unchanged, with its default settings and judge (gpt-5.4; gpt-5-mini for JSON recovery).
  • No system answered a question before its ingestion was complete (a readiness check gates each run).

Systems

  • 4Minds (Constellations): 4Minds prod, Constellations engine (WebSocket), GPT-OSS-120B served by 4Minds; one file per document. Leaderboard name: “4Minds Constellations (GPT-OSS-120B)”.
  • 4Minds (benchmark system prompt, local): 4Minds on the operator's local stack (minikube, branch vb/evals at 51f9f51df plus one local edit), Constellations engine (WebSocket), the same GPT-OSS-120B endpoint as prod; the persona's behavioral guidelines (the official prompt) replace the 4Minds response system prompt. Leaderboard name: “4Minds Constellations, benchmark system prompt, local build (GPT-OSS-120B)”.
  • GPT-OSS + LangChain: LangChain TokenTextSplitter (512 tokens, 10% overlap), text-embedding-3-large, FAISS; 100 chunks to the top 10 full documents; the official answer prompt; GPT-OSS-120B on Amazon Bedrock. Leaderboard name: “LangChain vector (text-embedding-3-large) + GPT-OSS-120B”.
  • GPT-OSS + GraphRAG: Microsoft GraphRAG 3.3.0, fast indexing method with default settings (1,200-token chunks, noun-phrase graph, community reports by GPT-OSS-120B), text-embedding-3-large; the local search context (community level 2) in the official answer prompt; GPT-OSS-120B on Amazon Bedrock. Leaderboard name: “Microsoft GraphRAG 3.3.0 fast, local search (text-embedding-3-large) + GPT-OSS-120B”.
  • GPT-OSS + GraphRAG (standard): Microsoft GraphRAG 3.3.0, standard indexing method with default settings (1,200-token chunks, LLM entity and relationship extraction, description summaries and community reports by GPT-OSS-120B), text-embedding-3-large; the local search context (community level 2) in the official answer prompt; GPT-OSS-120B on Amazon Bedrock. Leaderboard name: “Microsoft GraphRAG 3.3.0 standard, local search (text-embedding-3-large) + GPT-OSS-120B”.
  • GPT-OSS + RAGFlow: RAGFlow v0.27.2 (self-hosted), naive chunking (512 tokens, DeepDOC), text-embedding-3-large; POST /api/v1/retrieval with the default chat-assistant settings (6 chunks, hybrid keyword + vector search with vector weight 0.3, similarity threshold 0.2, no reranker); the chunks in the official answer prompt; GPT-OSS-120B on Amazon Bedrock. Leaderboard name: “RAGFlow v0.27.2 hybrid search (text-embedding-3-large) + GPT-OSS-120B”.
  • Gemini + File Search (first run): Gemini Developer API (Interactions API), gemini-3.8-flash with the File Search tool (top_k 5 per search; Gemini default temperature and thinking level); one store file per document with the File Search default chunking and embedding; the official instructions as the system instruction. Leaderboard name: “Gemini File Search (gemini-3.8-flash), first run”.
  • Gemini + File Search (3 attempts)*: The first-run folder of Gemini + File Search with up to two more attempts for its failed questions (same settings; the third attempt with a 300 s client timeout). Leaderboard name: “Gemini File Search (gemini-3.8-flash), 3 attempts”.
  • GPT-OSS, no RAG: GPT-OSS-120B on Amazon Bedrock with the official answer prompt and an empty Context Documents section (world-knowledge baseline). Leaderboard name: “GPT-OSS-120B, no retrieval”.
Read before you share

Notes and caveats

  • Pilot: 50 of 500 questions, stratified by question type (2 to 17 per type). The judge (gpt-5.4) is not fully repeatable. Do not rank systems from this table.
  • Corpus slice: 10,000 of 511,958 documents (the 74 gold documents of the pilot questions plus 9,926 random others). Retrieval is easier than on the full corpus, so these scores are not comparable with the public leaderboard.
  • Official default settings: a retrieved document that is not gold can become gold for that system when 3 judges agree (correction). Recall and invalid extra documents then use a different gold list for each system. The corrected-question count is in the table.
  • The official scorer skips a question with no answer and no documents; that question is not in the official averages. The column 'Overall, missing = 0' counts such a question as 0 over all pilot questions.
  • GPT-OSS-120B on Amazon Bedrock: temperature 0.3, 4,096 max tokens, reasoning effort medium (the 4Minds server defaults), for every system except the two 4Minds rows, which use the 4Minds GPT-OSS-120B deployment, and Gemini + File Search, which uses gemini-3.8-flash.
  • 4Minds: the document IDs come from the chunk document_title (file name <dsid>_<title>.txt), in chunk score order. The instructions of the official prompt are the persona's behavioral guidelines; 4Minds builds its own context and has no per-request system prompt, temperature or max-token setting.
  • 4Minds ingestion time: setup.json counts only from the restart of the wait (21:36 UTC). The upload started at 21:22 UTC and the chunk count did not change after 21:39 UTC, so the ingestion took about 17 minutes (then 15 minutes of stable wait).
  • 4Minds local: not the prod release. Local edit in constellations/assembler/prompts/preliminary_response_prompt.py: when the persona has behavioral guidelines, they replace PRELIMINARY_RESPONSE_SYSTEM (which asks for markdown and bold). The rest of the 4Minds prompt stays, including the DOCUMENT SUMMARIES section ('structure your coverage'); the stored document summaries are markdown. 26 of 50 answers have bold text (prod: 43 of 50). The document IDs come from the chunk document_title, as for prod.
  • 4Minds local: qst_0027 has no context. The Graph Engine timed out (15 s) on the local stack, and the system answered without chunks; prod had 10 chunks for this question. The answer is kept and scored.
  • 4Minds local scoring: the first pass hung on qst_0362 (no reply on 3 judge connections for 8 minutes) and was stopped; a second pass scored that question. The judge usage of the first pass is probably not in the recorded judge cost.
  • 4Minds local ingestion: the time is the whole setup step (upload, ingestion from 13:04 to 14:05 UTC, then 15 minutes of stable wait). Final chunk count 27,901, the same as prod. The build status was still 'enhancing' during the answers (document summaries still being written).
  • LangChain: a copy of the official vector baseline (index_document_vectors.py and vector_retrieval.py) with LangChain parts in place of Qdrant. The official README says 1,024-token chunks; the code uses 512 tokens with 10% overlap, and we follow the code.
  • GraphRAG: the context is the output of the official local search context builder (reports, entities, relationships and source text units, at most 12,000 tokens), given as one context in the official answer prompt; GraphRAG's own answer prompt is not used. The document IDs are the documents of the text units in the 'sources' table.
  • GraphRAG index: the community-report calls use GraphRAG's default call settings, not the Bedrock settings of the answer calls. Bedrock's JSON mode often puts a '{' in front of the reply; the hub repairs it in memory (audit/patches/graphrag-3.3.0-gptoss-json-repair.py). 117 of 16,179 communities (0.72%) have no report because the reply stayed invalid.
  • GraphRAG latency: the search is single-threaded Python over 5.66 million relationships. With 8 parallel workers the questions wait for each other, so the recorded median latency (about 108 s) is mostly waiting; one search alone took 12 to 15 s.
  • GraphRAG method: this row is not representative of GraphRAG. The fast method writes no entity descriptions (all 73,507 are empty), so local search compares the question only with entity names and often picks generic phrases. A test on 500 documents (the 74 gold documents plus 426 others, same settings) found 17 of 74 gold documents with the fast method and 52 of 74 with the standard method (LLM entity extraction); see the check_graphrag_fast_goldplus and check_graphrag_standard_goldplus steps in audit/audit.log. The row GPT-OSS + GraphRAG (standard) is a standard build of the same slice.
  • GraphRAG ingestion: the build stopped once in its last step (the OpenAI account had no credits) and that step ran again from the GraphRAG cache. The time is the sum of the two runs, without the wait.
  • GraphRAG (standard): the same answer path as the fast row (the official local search context builder, at most 12,000 tokens, as one context in the official answer prompt; document IDs from the 'sources' table). Only the index is different: 121,944 entities with descriptions and 256,481 relationships.
  • GraphRAG (standard) index: the same JSON repair of the Bedrock replies as the fast row (audit/patches/graphrag-3.3.0-gptoss-json-repair.py; 19,100 replies repaired). 53 of 21,727 communities (0.24%) have no report because the reply stayed invalid.
  • GraphRAG (standard): the index (16.6 h at 16 parallel LLM requests, about USD 102), the answers and the score were made on the operator's Linux machine (victormini1) with the same corpus slice (same corpus_sha256 as the fast index), code and scorer; the scoring environment uses the package versions of envs/pip_freeze_erag.txt. The answer latency (median 11 s, 8 parallel workers) is much lower than the fast row because the graph has fewer relationships.
  • RAGFlow: the context is the 6 chunks of the RAGFlow retrieval API, in RAGFlow rank order, each chunk as one context document in the official answer prompt; RAGFlow's own chat prompt is not used. The document IDs are the documents of these chunks (documents.json maps the RAGFlow document IDs).
  • RAGFlow ingestion: RAGFlow ran in Docker (WSL2) on a separate Windows PC; the Mac sent the searches over the local network. The time (upload 281 s + parse 8,385 s) depends on the CPU of that PC. The cost is only the embedding tokens that RAGFlow counted. setup.json on the Mac was restored from the step log of the setup run (same values), and documents.json was read again from the server.
  • Gemini + File Search: the answer model is gemini-3.8-flash, not GPT-OSS-120B, so this row changes the model and the retrieval together. It is a managed RAG product row, not a retrieval comparison with the GPT-OSS rows.
  • Gemini + File Search: the document IDs are the dsid metadata of the chunks that the answer cites, in citation order. File Search has no search-only API and returns only the cited chunks, not all the chunks that the tool read, so recall and invalid extra documents use the cited documents. `context` holds the cited chunk text.
  • Gemini + File Search (first run): 8 of 50 questions have no answer (qst_0023, qst_0027, qst_0036, qst_0267, qst_0329, qst_0385, qst_0489, qst_0492; 3 basic, 2 info_not_found, 1 semantic, 1 intra_document_reasoning, 1 constrained). After 90 to 120 s of searches, the Gemini API returned HTTP 400 'Model generated too many tool calls. Please retry the request.' The runner does not retry HTTP 400, so each question stopped at its first HTTP 400. These are failures of the system: the official averages skip them, and 'Overall, missing = 0' counts them as 0. The row Gemini + File Search (3 attempts)* gives these 8 questions two more attempts.
  • Gemini + File Search: Gemini decides how many searches to make (1 to 22 per answered question, median 2.5), so the system is not one-shot. The cost is in the retrieved tokens: the recorded cost of the 42 answers is USD 4.34 (median USD 0.02, maximum USD 0.73 for 22 searches). The usage of the 10 failed attempts (8 HTTP 400 replies and 2 earlier attempts that the runner retried) is not recorded, so the real cost is higher.
  • Gemini + File Search: the official instructions are the system instruction and the question is the input (as for 4Minds); Gemini builds the context itself. Each request filters on the store metadata corpus_sha256 of data/pilot_corpus.json.
  • Gemini + File Search ingestion: the store was made on 2026-10-11 outside setup_gemini.py (probably from another machine), and the hub has no record of the upload or its cost. shared/gemini/setup.json is a check of the store from the API on 2026-10-12 (10,000 active documents; dsid and text sha256 equal to the local corpus). The time is from the first document createTime to the last updateTime.
  • * Gemini + File Search (3 attempts): 6 of 50 questions (12%) have no answer after 3 attempts: qst_0023, qst_0027, qst_0036 (basic), qst_0267 (semantic), qst_0489, qst_0492 (info_not_found, both questions of this type). Each attempt ended with HTTP 400 'Model generated too many tool calls' from the Gemini API after 87 to 119 s of searches; this is a limit of the system, not a client timeout. The official averages skip these questions; 'Overall, missing = 0' counts them as 0. Correctness, completeness and recall are averages over the 44 answered questions only.
  • Gemini + File Search (3 attempts): a copy of the first-run folder (answers, judge results and corrected gold lists of the 42 answered questions). Attempt 2 (same settings and command) answered qst_0329 and qst_0385. Attempt 3 for the other 6 used a 300 s client timeout instead of 120 s, to rule out a client timeout (one attempt for qst_0492 had no reply after 300 s; its automatic retry ended with the same HTTP 400). score.py resumed, so the judge scored only the 2 new answers; the 42 shared judge results are identical to the first run. The attempt-2 folder is in _superseded_retry2/.
  • Gemini + File Search (3 attempts): the other rows had one attempt per question (retries only for network and rate-limit errors); this row had up to three attempts for its failed questions.
  • Gemini + File Search (3 attempts): the judge cost includes the first-run judge cost (copied score manifest); attempt 2 added USD 0.08. The recorded answer cost is USD 4.81 (first run USD 4.34, attempt 2 USD 0.47); the usage of the 24 failed attempts (20 HTTP 400 replies and 4 earlier attempts that the runner retried) is not recorded, so the real cost is higher.
  • No RAG: the official prompt says to answer only from the documents, and the document section is empty. The company is synthetic, so world knowledge cannot answer most questions.
